# 001 · 提示工程基础

> 本文用大白话回答：提示工程到底是啥？为什么"同一个模型、换个问法"结果差那么多？一个好提示由哪些零件拼成？零样本、少样本、System/User/Assistant 这些词到底在说什么？
>
> **零基础读法**：先读第二、三节对照表理解"给实习生派活"；第四节收拢术语；第五节完整改造案例建议亲手复制 prompt 试一次；第七节自测后再看总结。

## 一、一句话先说清

**提示工程（Prompt Engineering，"设计怎么跟大模型说话"的手艺）= 把你的需求说清楚，让模型一次就答到点子上。**

- 你写给模型的那段话叫**提示（Prompt，也就是"你给模型下的指令"）**。
- 提示工程**不改模型、不训练模型**，只优化"你怎么问"——问法变了，答案质量就可能天差地别。

| 你动什么 | 提示工程 | 微调 / RAG |
| --- | --- | --- |
| 模型权重 | 不动 | 要动（微调）或外挂知识库（RAG） |
| 成本 | 几乎为零，改字就行 | 要数据、算力、工程 |
| 适合 | 先快速试、格式约束、角色设定 | 模型真不会、或需要私有知识 |

**实用顺序**：先调提示 → 仍不够再考虑 [RAG](../05-大语言模型与Transformer/004-检索增强生成RAG.md) 或微调（见 [05/003 预训练与微调](../05-大语言模型与Transformer/003-预训练与微调.md)）。

## 二、打个比方：给实习生派活

同样一个需求，随便一问和精心设计地问，效果完全不同。就像给一个刚来的实习生派活：

- 含糊地说"帮我写个东西" → 他一头雾水，交上来的多半不是你要的；
- 清楚地说"帮我写一封**面向新客户**的**产品介绍邮件**，语气**专业友好**，**200 字以内**，包含**三个卖点**" → 他一次就能交出满意的稿子。

区别不在实习生的能力，而在**你有没有把话说清楚**。模型也一样：

| 生活里的做法 | 提示工程里的对应 | 效果 |
| --- | --- | --- |
| 交代清楚"做什么" | 写明确的**指令（Instruction）** | 模型不跑偏 |
| 给背景资料 | 提供**上下文（Context）** | 模型有据可依 |
| 说清"要什么格式" | 约束**输出格式** | 结果能直接被程序读 |
| 指定"用什么口气、什么身份" | 设定**角色/风格** | 语气对味 |

**说清楚：要做什么、背景是什么、给谁看、什么格式、什么约束——这就是提示工程的精髓。**

再补一条：**模型有"注意力预算"**（上下文长度有限）。废话太多会像实习生听了一小时背景却忘了核心任务——所以**精准比冗长更重要**（见第六节误区）。

## 三、它到底解决什么问题

### 问题 1：模型不知道你到底想要什么

模型不会读心，你说得越含糊，它越只能靠"平均猜测"来回答——就像问实习生"写点东西"，它只能猜你要邮件还是 PPT。

| 场景 | 朴素做法（含糊问） | 更好做法（说清楚） |
| --- | --- | --- |
| 让模型翻译 | "翻译一下这段" | "把下面文本**翻译成英文**，**保留专业术语**，不要解释" |
| 让模型总结 | "总结这篇文章" | "用**三个要点**总结，每点**不超过 20 字**，面向**非技术读者**" |
| 让模型写代码 | "写个排序" | "用 **Python 3**，实现**稳定**归并排序，带**类型注解**和** doctest 示例**" |

一个高质量提示通常由这几个"零件"拼成：

| 要素 | 作用 | 例子 |
| --- | --- | --- |
| 指令（Instruction） | 明确任务 | "把下面文本翻译成英文" |
| 上下文（Context） | 提供背景/资料 | 相关文档、对话历史 |
| 输入数据 | 要处理的内容 | 待翻译的文本 |
| 输出格式 | 约束返回形式 | "用 JSON 返回，含 title 和 summary 字段" |
| 角色/风格 | 设定语气 | "你是一位资深律师" |

**拼装顺序建议（非硬性）**：角色/规矩 → 任务指令 → 背景资料 → 输入 → 格式要求。这样模型先知道"我是谁、规矩啥"，再看到具体活。

### 问题 2：任务很特殊时，光"下命令"不够——得"给样板"

有些任务格式很怪（比如固定 JSON 字段、特定标签），光靠一句指令模型未必领会，这时**给几个例子让它照葫芦画瓢**更管用。这就引出两种问法：

- **零样本（Zero-shot，"零个示例"）**：只给指令、不给示例，直接让模型做。常规任务（翻译、摘要）用它就够。
- **少样本（Few-shot，"少量示例"）**：在提示里塞几个"输入 → 输出"示例，模型照着仿写。示例一般 **1～5 个**即可，再多占上下文且收益递减。

| 问法 | 何时用 | 例子 |
| --- | --- | --- |
| 零样本 | 任务常见、格式简单 | "把下面文本译成英文：…" |
| 少样本 | 格式特殊、领域术语多 | 给 2 条"评论→JSON"样板再让模型分析新评论 |

> 打比方：零样本像"直接口头交代任务"；少样本像"再附上两份做好的样板给他参考"。任务越不常规、格式越特殊，给样板（少样本）越有效。

少样本之所以有效，靠的是大模型的**上下文学习（In-Context Learning，"看着提示里的例子临时学会照做"）**能力——**它不需要重新训练、不改动模型参数**，只是从你给的例子里现学现用。注意：这是**推理时**的临时能力，不是把例子"写进权重里"。

### 问题 3：多轮对话里，"谁在说话"要分清

对话式 API 通常把消息分成三种**角色（Role）**，好比一台戏里的不同角色牌：

| 角色 | 大白话 | 作用 | 例子 |
| --- | --- | --- | --- |
| **System** | "总导演的规矩" | 设定全局身份与规则，优先级最高 | "你是严谨的医学助手，不确定就说不知道" |
| **User** | "用户这次说的话" | 用户的具体请求 | "帮我看看这个化验单" |
| **Assistant** | "模型之前的回复" | 多轮时作为对话历史，让模型知道前面说过啥 | 上一轮模型说过的话 |

**合理使用 System 消息，能稳定地约束模型的行为**——相当于开场就把规矩立好，后面每一轮 User 消息都在这套规矩下回答。换任务时 often 换 System，而不是在历史里堆规则。

```text
[System] 你是 JSON 提取助手，只输出 JSON，不要 markdown。
[User]   分析这条评论：物流很快但包装破损。
[Assistant] {"sentiment":"负面","issues":["包装破损"]}
[User]   分析：客服态度很好，产品一般。
```

多轮对话时，**Assistant 历史**让模型保持格式一致；但若历史太长，旧规则可能被"冲淡"，必要时在 User 里再次强调格式。

## 四、专业视角（与大白话对齐）

把前面的大白话收拢成严谨说法：

- **提示工程**：通过设计输入文本（提示），在**不改变模型参数**的前提下，引导大语言模型产生期望输出的方法。对齐前面：就是"只改怎么问，不动模型本身"。
- **零样本 / 少样本**：提示中提供的示例数量为 0 或少量。少样本依赖**上下文学习**——模型在推理时（而非训练时）从提示内的示例归纳出任务模式。对齐前面：就是"照葫芦画瓢，且不用重新训练"。
- **角色消息**：System / User / Assistant 三类消息构成对话上下文，其中 System 提供最高优先级的行为约束。对齐前面：就是"总导演的规矩 + 用户的话 + 模型的历史发言"。

**和训练的关系（易混点）**：

| 概念 | 何时发生 | 是否改权重 |
| --- | --- | --- |
| 提示工程 / 少样本 | 每次推理 | 否 |
| SFT 微调 | 训练阶段 | 是 |

少样本看起来像"教模型"，但只是**临时**模仿；要永久学会新格式，仍需微调或反复在 System 里写死规则。

## 五、案例解析：从模糊到精确的提示改造

**任务**：让模型从一段客户评论中提取情感和关键问题。

- **模糊提示**：`分析这条评论：{评论}` → 模型可能返回一大段自由发挥的文字，格式不定、难以程序化使用。
- **精确提示**（角色 + 格式 + 少样本）：

```text
你是评论分析助手。请判断情感（正面/负面/中性）并提取最多 3 个关键问题。
仅返回 JSON，格式：{"sentiment": "...", "issues": ["..."]}

示例：
评论：物流很快但包装破损。
输出：{"sentiment": "负面", "issues": ["包装破损"]}

评论：{待分析评论}
输出：
```

改造后，模型稳定返回结构化 JSON，可直接被下游程序 `json.loads` 解析。**同一个模型，靠提示设计就把"不可用"变成了"生产可用"**——这正是提示工程的价值。

**逐步对照改了什么**：

| 改造点 | 模糊版缺什么 | 精确版怎么补 |
| --- | --- | --- |
| 角色 | 无 | "你是评论分析助手" |
| 输出格式 | 无 | "仅返回 JSON" + 字段说明 |
| 少样本 | 无 | 一条完整输入输出示例 |
| 任务边界 | 无 | "最多 3 个关键问题" |

对照第四节：这里同时用上了**角色**、**输出格式**、**少样本**三个零件。若仍偶发 markdown 包裹 JSON，可在 System 里加"禁止 ```json 代码块"。

## 六、常见误区与边界

- **误区："提示越长越详细越好"**：冗余信息会稀释重点、浪费**上下文窗口**（模型一次能读的最大长度）；应精准而非冗长。
- **误区："模型没做好一定是模型笨"**：很多时候是提示没说清；**先优化提示**再考虑换模型/微调/RAG。
- **误区："少样本示例可以随便写"**：示例中的错误格式会被模型学走；示例应代表你想要的**理想输出**。
- **边界**：提示工程无法凭空注入模型不具备的知识（该用 [RAG](../05-大语言模型与Transformer/004-检索增强生成RAG.md)）或改变其根本能力（该用微调）；对需要**多步推理**的任务，见 [002 思维链与推理](./002-思维链与推理.md)。

## 八、一句话总结

- 好提示 = 明确指令 + 必要上下文 + 输出格式 + 角色约束；少样本靠示例引导。
- 善用 System 消息稳定行为；先调提示，再考虑 RAG 或微调。
